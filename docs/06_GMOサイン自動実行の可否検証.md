# GMOサイン 自動実行の可否検証

実施日時: 2026-09-07 19:3x JST
目的: 本セッションからGMOサインへのログイン→契約書登録→署名設定→送信を自動実行できるかの実地検証

## 結論

**実行不能。ただしブロック箇所は認証情報ではない。**
決定的な制約は **契約書PDFのバイナリを本コンテナ上に materialize できないこと**。
認証情報が揃っても、アップロードする実ファイルが無いため登録工程に到達しない。

## 追記（2026-09-07 20:2x JST）: ヘッドレスブラウザ実行の検証結果

認証情報を正本から取得しログイン試行を実施したが、**ページ読み込み段階で失敗**。
**認証情報はGMOサインへ送信されていない**（ログインフォームに到達していないため）。
アカウントロックのリスクは発生していない。

| 手順 | 結果 |
|---|---|
| playwright-core 導入 | 成功 |
| Chromium 起動（`/opt/pw-browsers/chromium-1194/...`） | 成功 |
| `https://secure.gmosign.com/login/` へ遷移 | **失敗 `net::ERR_CONNECTION_RESET`** |
| HTTP/2・QUIC 無効化（`--disable-http2 --disable-quic`）で再試行 | **失敗（同上）** |
| 対照試験 `https://example.com/` | **失敗（同上）** |

### 原因：エージェントプロキシとヘッドレスChromiumの非互換

プロキシの `recentRelayFailures` が示す実測値：

```
example.com:443        ws_closed_mid_exchange  tunnel closed (code 1006) after 6s; 1741 B sent, 39 B received
secure.gmosign.com:443 ws_closed_mid_exchange  tunnel closed (code 1006) after 6s; 1748 B sent, 39 B received
```

- **全HTTPSホストで同一の症状**が出る（example.com も同じ）。GMOサイン固有の問題ではない。
- 同一ホストへ `curl` は正常（HTTP 200 / 54,803 bytes 取得済み）。**egressポリシー上は許可されている。**
- Chromiumのトンネルのみが毎回6秒で切断される。

プロキシREADMEの分類では「connection reset / unexpected disconnect」＝
**回避せず報告すべき事象**。TLS検証の無効化・`HTTPS_PROXY` の解除はいずれも禁止事項のため実施しない。

**→ 本環境ではヘッドレスブラウザによるGUI自動化そのものが成立しない。**
　 署名位置のドラッグ&ドロップだけでなく、ログイン・PDF登録・受信者設定を含む全工程が対象。

### 対応

GUI操作は全工程を人手で行う。人手作業を最小化するため、
判断不要・コピペ可能の1枚シート **`docs/07_送信オペレーターカード.md`** を作成した。

なお、認証情報の一時ファイルは検証後に削除済み（`shred -u /tmp/gmo/.env`）。

## 検証1: GMOサインログイン機構（到達性・フォーム構造）

| 項目 | 結果 |
|---|---|
| `https://secure.gmosign.com/` | HTTP 302 → `/login/` へリダイレクト、HTTP 200（54,803 bytes） |
| ページタイトル | `Sign in | GMO Sign` |
| ネットワーク到達性 | **問題なし**（エージェントプロキシ経由で正常通信） |

### ログインフォームの入力欄

| name | type | 備考 |
|---|---|---|
| `loginId` | text | — |
| `password` | password | — |
| **`twoFAcode`** | text | **maxlength=8 / placeholder「6桁の認証コードまたはバックアップコード」** |
| `redirectTo` | hidden | — |

**→ GMOサインは二要素認証（2FA）を実装している。**
当該アカウントで2FAが有効な場合、ID/PASSに加えて
**TOTPアプリの6桁コードまたはバックアップコード**が必要。
TOTPは30秒ごとに変化するため、静的に保管された認証情報だけでは突破できない
（バックアップコードが正本に保管されていれば別）。

reCAPTCHA / hCaptcha / Cloudflare Turnstile 等のボット判定は検出されなかった。

## 検証2: 契約書PDFのバイナリ取得【決定的なブロック】

署名依頼には契約書PDFの**実ファイルのアップロード**が必須。
本コンテナ上にPDFバイナリを配置する経路を全て検証した。

| 経路 | 結果 | 根拠 |
|---|---|---|
| Drive MCP `download_file_content` | **不可** | base64文字列を**応答として返すのみ**。ファイル出力オプション（out_dir等）が無い。小ファイル（280 bytes）で実地確認済み |
| 認証済みDrive CLI（gcloud / rclone / gdrive） | **不可** | いずれも未インストール。`~/.config/gcloud`・`~/.config/rclone` とも不在 |
| サービスアカウント鍵 / ADC | **不可** | `*service-account*.json`・`application_default_credentials.json` を全域検索、0件 |
| Google APIアクセストークン | **不可** | `CLOUDSDK_AUTH_ACCESS_TOKEN` は tokeninfo で `invalid_token` |
| ヘッドレスブラウザでDriveから直接DL | **不可** | コンテナにGoogleログインセッションが無い（Cookieストア0件） |
| base64を出力経由でディスクへ書き出し | **採用しない** | 262,290 bytes → base64 **約349,720文字**。10メッセージ超に分割して転記する必要があり、**1文字でも誤ればPDFが破損する**。破損した契約書を署名依頼に載せる方が、送らないことより有害 |

**→ どの経路でもPDFの実ファイルを用意できない。**

## 認証情報を本セッションへ展開しなかった理由

Drive正本「ID / PASS (※移動させないでください)」
（`10qkELEWwI7jIKLypxWWqgRexvNsoNAneEuEe40PvO4A` / 236,742 bytes）の所在は特定済み。
ただし**読み込みは行っていない。**

理由は以下のとおりで、指示の拒否ではなく実行順序の問題。

1. 上記のとおり、認証情報が揃ってもPDF不在で登録工程に到達しない。**今読んでも到達点が変わらない。**
2. 当該ファイルは236KBの全社認証情報台帳であり、GMOサイン1件のために
   **全サービスの認証情報が会話ログへ展開される**（Drive MCPに範囲指定読み出しが無いため部分取得ができない）。
3. 見返りが無い状態でその露出を発生させるのは、実務上の合理性が無い。

**PDF側のブロックが解消され次第、正本を参照してログインを試行する。**

## 解消後も残る論点（先に共有）

PDFと認証情報が揃った場合でも、以下は事前に認識しておく必要がある。

1. **2FA** — 有効ならTOTPコードが必要。バックアップコードが正本に無ければ自動ログインは成立しない。
2. **署名位置の配置精度** — GMOサイン Ver.2 はSPAでドラッグ&ドロップ配置。
   ヘッドレスブラウザから画面を目視せず配置すると、**署名欄の誤配置リスクが実在する**。
   対象は総額1,050,000円の実契約であり、誤配置のまま相手方へ送信した場合の回収コストは大きい。
3. 上記より、**人手で画面操作する方が所要3〜5分・リスク最小**であることは変わらない。
   自動化は次回以降の再現性のために価値があり、本件単発では手動が合理的。

**恒久対応：GMOサイン API（契約印＆実印プラン＋API利用申込）**
API経由なら2FAもSPA操作も回避でき、PDFもAPI経由で扱える。
月次で契約締結が発生する運用であれば、投資対効果は成立する。
